Partition strategy — 30M+ messages
-- Bảng chính: partition by RANGE trên created_at CREATE TABLE messages ( id uuid DEFAULT gen_random_uuid(), conv_id uuid NOT NULL, sender_id uuid NOT NULL, type text NOT NULL DEFAULT 'text', content text, reply_to_id uuid, created_at timestamptz NOT NULL DEFAULT now(), deleted_at timestamptz, PRIMARY KEY (id, created_at) ) PARTITION BY RANGE (created_at); -- Tạo partition mỗi quý (3 tháng) -- Q1 2025: messages từ Jan–Mar 2025 CREATE TABLE messages_2025_q1 PARTITION OF messages FOR VALUES FROM ('2025-01-01') TO ('2025-04-01'); CREATE TABLE messages_2025_q2 PARTITION OF messages FOR VALUES FROM ('2025-04-01') TO ('2025-07-01'); -- ... tạo partition trước cho Q3, Q4, 2026...
Index quan trọng
Index 1 — Timeline scroll
Query chính khi user scroll lên: lấy N messages cũ hơn cursor theo conv_id.
CREATE INDEX idx_msg_conv_time
ON messages (conv_id, created_at DESC)
WHERE deleted_at IS NULL;
Index 2 — Jump to date
User click vào ngày trong calendar → jump tới vị trí đó.
CREATE INDEX idx_msg_conv_date
ON messages (conv_id, date_trunc('day', created_at));
Index 3 — Reply lookup
CREATE INDEX idx_msg_reply
ON messages (reply_to_id)
WHERE reply_to_id IS NOT NULL;

Tại sao partition by time — không phải by conv_id?
1
Hot data vs cold data rõ ràngPerf
Messages tháng này được query liên tục (hot). Messages 2 năm trước gần như không bao giờ load (cold). Partition by time → PostgreSQL chỉ scan partition hiện tại, bỏ qua hoàn toàn các partition cũ.
2
Archive tự độngOps
Partition 2023 không ai đọc nữa → move sang cold storage (S3/object store). Không cần DELETE, chỉ DETACH PARTITION và archive. Zero downtime.
3
Không partition by conv_id vì gì?Warning
Một số conversation rất lớn (group nhóm, channel all-hands) có thể có hàng triệu messages trong 1 partition → uneven distribution. Time-based luôn đều hơn.
Cursor-based pagination — không dùng OFFSET
!
OFFSET là anti-pattern cho chat. OFFSET 10000 vẫn scan 10000 rows trước khi skip → chậm dần theo thời gian. Dùng cursor (last message ID + timestamp) thay thế.
-- Load 30 messages CŨ HƠN cursor (scroll lên) SELECT id, conv_id, sender_id, type, content, created_at, reply_to_id FROM messages WHERE conv_id = $1 -- conversation AND created_at < $2 -- cursor timestamp AND deleted_at IS NULL ORDER BY created_at DESC LIMIT 30; -- Response trả về cursor cho lần load tiếp theo: -- { messages: [...], nextCursor: messages[29].created_at }

Jump to specific date
1
User chọn ngày từ calendar
Tìm message gần nhất với ngày đó làm điểm neo.
SELECT id, created_at FROM messages
WHERE conv_id = $1
AND created_at >= $date_start
ORDER BY created_at ASC LIMIT 1;
2
Load context window xung quanh
Lấy 15 messages trước + 15 messages sau điểm neo → user thấy ngữ cảnh đầy đủ.
-- 15 trước anchor
SELECT * FROM messages WHERE conv_id=$1
AND created_at < $anchor ORDER BY created_at DESC LIMIT 15;
-- 15 sau anchor
SELECT * FROM messages WHERE conv_id=$1
AND created_at >= $anchor ORDER BY created_at ASC LIMIT 15;

2 tầng search — local cache + server
1
Tầng 1: Drift local SQLite (< 300ms)Fast
Flutter search trong messages đã cache local (7 ngày gần nhất). Kết quả tức thì, không cần network. Dùng SQLite FTS5 extension.
-- Drift local FTS5
SELECT m.* FROM messages_fts
JOIN messages m ON m.id = messages_fts.id
WHERE messages_fts MATCH 'query*'
ORDER BY rank LIMIT 20;
2
Tầng 2: PostgreSQL full-text (server)Complete
Nếu user muốn search toàn bộ lịch sử → gọi API. PostgreSQL FTS với tsvector column + GIN index. Hỗ trợ tiếng Việt qua unaccent extension.
3
Tầng 3: Elasticsearch (scale lớn)Optional
Khi số lượng lớn hơn vài chục triệu và cần search phức tạp (fuzzy, multilang, snippet highlight). Overkill cho < 50 người — implement khi thực sự cần.
PostgreSQL FTS — setup tiếng Việt
-- Bước 1: Enable extensions CREATE EXTENSION IF NOT EXISTS unaccent; CREATE EXTENSION IF NOT EXISTS pg_trgm; -- trigram similarity -- Bước 2: Thêm cột tsvector (được tự cập nhật) ALTER TABLE messages ADD COLUMN search_vector tsvector GENERATED ALWAYS AS ( to_tsvector('simple', unaccent(coalesce(content, '')) ) ) STORED; -- Bước 3: GIN index trên tsvector CREATE INDEX idx_msg_fts ON messages USING GIN (search_vector); -- Bước 4: Trigram index cho partial match "api lo" CREATE INDEX idx_msg_trgm ON messages USING GIN (unaccent(content) gin_trgm_ops) WHERE deleted_at IS NULL;
Search query — 3 loại chính
-- 1. FULL-TEXT: "deploy production" SELECT m.*, conv.name AS conv_name, ts_headline('simple', unaccent(m.content), plainto_tsquery('simple', unaccent($query)), 'MaxWords=15, MinWords=5' -- snippet highlight ) AS headline FROM messages m JOIN conversations conv ON conv.id = m.conv_id JOIN conversation_members cm ON cm.conv_id = m.conv_id AND cm.user_id = $userId -- chỉ search conv mình có WHERE m.search_vector @@ plainto_tsquery('simple', unaccent($query)) AND m.deleted_at IS NULL ORDER BY ts_rank(m.search_vector, plainto_tsquery('simple', unaccent($query))) DESC, m.created_at DESC LIMIT 20; -- 2. PARTIAL MATCH: "api lo" → khớp "api login" WHERE unaccent(content) ILIKE unaccent($1) -- $1 = '%api lo%' -- trigram index tự kick in, không phải seq scan -- 3. SCOPED: search trong 1 conversation WHERE m.conv_id = $convId AND m.search_vector @@ plainto_tsquery(...) -- Nhanh hơn nhiều vì partition pruning

Local cache strategy (Drift)
1
Giữ 7 ngày gần nhấtDefault
Cache 7 ngày mỗi conversation. Đủ cho 99% use case, không ngốn storage điện thoại.
2
Eviction strategyLRU
Conversation không xem > 30 ngày → xóa cache local. Mở lại → fetch lại từ server.
3
Search localFTS5
Drift + SQLite FTS5 virtual table → search instant trong cached messages, không cần network.
