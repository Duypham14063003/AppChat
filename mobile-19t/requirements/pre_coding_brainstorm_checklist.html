MUST JWT strategy — access token + refresh token
Chưa quyết định rõ lifetime và rotation strategy. Đây ảnh hưởng trực tiếp tới UX (bị logout bất ngờ) và security.
Access token sống bao lâu? 15 phút (secure) hay 1 giờ (ít annoying hơn)?
Refresh token rotation: mỗi lần dùng refresh token → issue token mới và invalidate token cũ. Nếu token cũ được dùng lại → detect theft → logout tất cả sessions.
Multi-device: user login trên 3 thiết bị → mỗi device có refresh token riêng. Logout một device không ảnh hưởng device khác.
Token storage Flutter: flutter_secure_storage (Keychain iOS / Keystore Android). Desktop: encrypted file. Web: httpOnly cookie thay vì localStorage.
access_token_ttl: 15m (config)
refresh_token_ttl: 30d
Table: user_sessions (device_id, refresh_token_hash, last_used, expires_at)
MUST Odoo service account — scope và rate limit
Hiện tại plan dùng Odoo service account để gọi API. Cần thiết kế rõ ràng để không bị abuse.
Service account chỉ được phép làm gì? Read-only HR data? Hay cũng write (checkin/checkout)? Principle of least privilege.
Cache Odoo responses: user profile, payroll config, project list → cache Redis 5-15 phút. Không gọi Odoo mỗi request.
Odoo API rate limit? Cần biết limit để thiết kế queue hoặc circuit breaker nếu Odoo bị chậm.
MUST Message encryption — có cần E2E không?
Đây là quyết định quan trọng ảnh hưởng toàn bộ architecture. Cần quyết định trước khi code DB schema.
Option A — Transport only (TLS): Message lưu plaintext trong DB. Admin có thể đọc. Đơn giản, dễ implement search/backup. Phù hợp với internal tool.
Option B — E2E Encryption: Message mã hóa trên client, server không đọc được. Signal Protocol hoặc tự implement. Rất phức tạp, search không hoạt động, backup khó. Overkill cho internal app.
Khuyến nghị cho use case này: TLS + HTTPS + encrypted DB at rest là đủ. E2E thêm complexity không tương xứng cho internal company tool.
MUST Rate limiting & anti-spam
Internal app nhưng vẫn cần guard. Bot hoặc bug client có thể spam messages làm DB overload.
Message rate limit: tối đa 30 messages/phút/user. Implement ở NestJS WebSocket gateway bằng @nestjs/throttler.
File upload rate limit: tối đa 10 files/phút/user, max file size 50MB (config).
WebSocket reconnect flood: exponential backoff ở Flutter client — 1s, 2s, 4s, 8s... max 60s. Không reconnect liên tục khi mất mạng.

MUST Conflict resolution — gửi tin khi offline
User gõ và gửi tin khi không có mạng. App phải queue và retry khi có mạng. Cần define behavior rõ ràng.
Client-side queue: Message được assign UUID ngay trên client → lưu vào Drift với status=pending → gửi lên server khi có mạng → server confirm với same UUID.
Duplicate prevention: Server dùng UUID làm idempotency key. Message gửi lại 3 lần vẫn chỉ insert 1 lần.
Order đảm bảo: Client_generated_at (local time) dùng để sort optimistic. Server_created_at (UTC) dùng để sort chính thức sau khi sync. Có thể có chênh lệch nhỏ — acceptable.
Failed permanently: Sau 5 lần retry thất bại → đánh dấu "Gửi thất bại" + nút Retry. Không silent drop.
enum MessageStatus { pending, sent, delivered, read, failed }
Drift: messages table thêm cột local_status, retry_count, client_id
MUST Reconnect & missed messages sync
App bị background 30 phút, có 20 messages mới. Khi foreground lại phải sync đúng, không miss.
Last seen timestamp: Mỗi device lưu last_synced_at. Khi reconnect WebSocket → gửi last_synced_at → server trả về tất cả messages mới hơn.
FCM backup: Nếu WebSocket miss event → FCM push là safety net. App foreground → merge FCM payload với WS stream.
Delta sync endpoint: GET /sync?since=timestamp trả về messages, read receipts, reactions thay đổi. Gọi khi app foreground sau > 5 phút background.
SHOULD HR checkin offline — GPS cache
Nhân viên checkin ở vùng sóng yếu. App phải ghi nhận chính xác thời điểm checkin, không phải thời điểm có mạng.
Capture locally: Khi bấm checkin → lưu ngay (timestamp, GPS coords, device_id) vào Drift. Status = pending_sync.
Sync khi có mạng: Gửi lên server với original_timestamp. Server dùng original_timestamp, không phải received_at.
Anti-cheat: Server validate GPS coordinates hợp lệ, timestamp không quá 24h cũ, không checkin 2 lần trong cùng ngày.
MUST Môi trường — dev / staging / production
Cần 3 environment riêng trước khi bắt đầu code. Không có staging → deploy thẳng lên production → nguy hiểm.
Dev: Local machine. DB local, Redis local. Flutter app connect localhost.
Staging: Server riêng (có thể VPS nhỏ). Dữ liệu test, không dữ liệu thật. Team test trước khi release.
Production: Server chính. Backup tự động. Monitoring. Zero-downtime deploy.
Flutter flavor: Mỗi environment là một flavor riêng — khác màu app icon, khác bundle ID, khác API URL. Không nhầm lẫn staging với production.
Flutter flavors: dev | staging | prod
flutter run --flavor dev -t lib/main_dev.dart
flutter build apk --flavor prod -t lib/main_prod.dart
MUST CI/CD pipeline
Không có CI/CD → deploy tay → lỗi do human error → mất tin cậy với team.
Backend (NestJS): GitHub Actions → test → build Docker image → push registry → deploy tới server (zero-downtime rolling update).
Flutter mobile (iOS/Android): GitHub Actions + Fastlane → build → upload TestFlight (iOS) / Internal Track (Android) tự động.
Flutter desktop (Windows/macOS): Build artifact, upload tới internal distribution server. User download từ đó hoặc auto-update.
DB migrations: TypeORM migrations chạy tự động khi deploy. Không bao giờ sửa DB tay trên production.
MUST Monitoring & alerting
App internal nhưng vẫn cần biết khi có sự cố. Không monitor → biết server chết khi user báo cáo.
Uptime monitoring: BetterUptime hoặc UptimeRobot (free). Ping /health endpoint mỗi 1 phút. Alert qua Telegram bot (ironic) hoặc email khi down.
Error tracking: Sentry (free tier đủ dùng). NestJS backend + Flutter client đều integrate. Biết ngay khi có exception.
Performance monitoring: Track p95 API latency. Alert khi > 500ms. Đơn giản nhất: log slow queries PostgreSQL (log_min_duration_statement = 200ms).
Business metrics: Daily active users, message volume, call duration. Dùng để justify cost và plan scale.
SHOULD Backup strategy
PostgreSQL: pg_dump tự động mỗi đêm → upload S3/Bunny.net. Giữ 30 ngày. Test restore mỗi tháng.
Redis: AOF persistence. Redis data là cache/queue — mất được (sẽ tự rebuild), nhưng vẫn nên persist.
Bunny.net files: Files attachment đã lưu trên CDN. Bunny.net tự redundant. Nhưng nên enable geo-replication.
RTO/RPO: Mục tiêu là restore trong 2 giờ, mất tối đa 24h data. Xác định ngay để chọn backup frequency.
MUST Timezone & ngày lễ
Timezone: Tất cả timestamp lưu UTC trong DB. Flutter convert sang timezone local của user khi hiển thị. Không bao giờ lưu local time.
Ngày lễ Việt Nam: Cần table ngày lễ — ảnh hưởng tới tính công chuẩn, OT rate. Cập nhật hàng năm. Admin có thể add custom holidays.
Kỳ lương cross-month: Nếu kỳ lương 20/3 → 19/4, logic tính công phải handle đúng, không bị off-by-one error ở ngày đầu/cuối kỳ.
Table: holidays (date, name, type: national|company|custom)
All timestamps: timestamptz (UTC) — không dùng timestamp without tz

SHOULD Odoo sync strategy — realtime hay batch?
Realtime sync: Mỗi checkin → push ngay lên Odoo. Nếu Odoo chậm/down → checkin bị delay. Cần circuit breaker.
Batch sync: Lưu vào app DB trước → BullMQ job sync lên Odoo mỗi 15 phút hoặc cuối ngày. Odoo down không ảnh hưởng UX. Khuyến nghị.
Conflict khi Odoo có data khác: AI app là source of truth cho attendance data → Odoo là destination. Không 2-way sync để tránh conflict.
MUST Testing strategy — cần test gì trước tiên?
Với team nhỏ, không thể test mọi thứ. Cần chọn đúng điểm để test có hiệu quả cao nhất.
Business logic (highest ROI): HR tính công, OT, payroll calculation. Sai ở đây → ảnh hưởng lương. Unit test bắt buộc 100% coverage.
API integration tests: Test các endpoint critical: auth, send message, checkin/checkout. Dùng Supertest + test DB riêng.
WebSocket tests: Test message delivery, typing indicator, read receipt. Dùng Socket.io mock client.
Flutter widget tests: Test chat bubble render, message list scroll. Bỏ qua e2e test ban đầu — quá chậm để setup.
Priority: HR calc unit tests > API integration > WS > Flutter widget
SHOULD Load testing — trước khi release
WebSocket concurrent connections: Simulate 50 users online cùng lúc, gửi messages liên tục. Dùng k6 hoặc Artillery.
Message burst: Group chat, 10 người gửi cùng lúc → fan-out queue phải xử lý. Test xem BullMQ có bottleneck không.
File upload concurrent: 5 user upload file 10MB cùng lúc → Bunny.net bandwidth + NestJS memory.
MUST App update strategy — force update
Internal app — bạn kiểm soát hoàn toàn việc update. Cần cơ chế ép user update khi có breaking changes.
Version check: Mỗi khi app start → gọi GET /app/version → server trả về { min_version, latest_version }. Nếu app_version < min_version → force update dialog.
Desktop auto-update: Flutter desktop dùng auto_updater package. Khi có version mới → notify user → download + install tự động trong background.
Mobile: iOS qua TestFlight (internal distribution), Android qua APK direct download hoặc Play Store internal track. Không qua App Store public.
API versioning: Prefix /api/v1/. Khi có breaking changes → /api/v2/ chạy song song trong 2 tuần để app cũ không bị crash ngay.

DECIDE Monorepo hay separate repos?
Option A — Monorepo: 1 repo chứa cả Flutter + NestJS. Dễ share types/models. CI/CD phức tạp hơn. Phù hợp team nhỏ.
Option B — Separate repos: flutter-app repo + nestjs-api repo. Độc lập, deploy riêng. Cần giữ API contract sync bằng tay hoặc OpenAPI schema.
Khuyến nghị cho team nhỏ: Monorepo với Nx hoặc Turborepo. Shared TypeScript types giữa Flutter (via dart gen) và NestJS.
